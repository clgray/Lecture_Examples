# Анализ паттерна Strategy

**Задача:** обеспечить получение логов из разных источников без изменения основного алгоритма их обработки.

**Решение:** использовать интерфейс `ILogImporter`, который определяет метод `GetLogs()`. Его реализуют классы `FileLogImporter` и `SystemLogImporter`, отвечающие за получение записей из разных источников.

**Как работает:** класс `LogProcessor` принимает реализацию `ILogImporter` через конструктор. Затем он получает список логов, сортирует записи и выполняет их обработку.

**Почему:** такой подход позволяет менять источник логов без изменения класса `LogProcessor`. Для добавления нового источника достаточно создать новую реализацию интерфейса `ILogImporter`.

**Преимущество:** разделение ответственности упрощает расширение и поддержку программы.

## Анализ нарушений SOLID

| Принцип | Где обнаружено нарушение | В чём заключается проблема | Как исправить |
|---|---|---|---|
| **SRP** — принцип единственной ответственности | `LogProcessingModule` | Класс выполняет множество задач: загружает конфигурацию, открывает соединения, читает файлы, разбирает и фильтрует записи, форматирует и сохраняет логи. У него слишком много причин для изменения. | Разделить обязанности между отдельными компонентами: чтение, парсинг, фильтрация, форматирование и запись. |
| **OCP** — принцип открытости/закрытости | Методы `OpenSinks()`, `Write()`, `Format()`, `SeverityToInt()` | Для добавления нового приёмника или формата необходимо изменять существующие методы и добавлять новые ветви `switch`. | Использовать отдельные реализации приёмников и форматтеров, чтобы новые варианты добавлялись без изменения основной логики. |
| **ISP** — принцип разделения интерфейсов | Интерфейс `ILogSink` | Интерфейс содержит методы `BeginTransaction()`, `Rotate()`, `SetConsoleColor()` и другие, которые не нужны всем приёмникам. Например, консольному приёмнику не нужны транзакции, а файловому — управление цветом консоли. | Разделить большой интерфейс на небольшие интерфейсы с конкретными обязанностями. |
| **DIP** — принцип инверсии зависимостей | Поля и методы `LogProcessingModule` | Основной класс напрямую зависит от конкретных реализаций: `File`, `StreamWriter`, `Console`, `FakeDbConnection`. Это затрудняет замену компонентов и написание изолированных тестов. | Передавать необходимые зависимости через конструктор, используя подходящие абстракции. |

### Дополнительные проблемы

- Метод `ParseLine()` возвращает `null` при ошибке разбора, из-за чего вызывающий код должен самостоятельно проверять результат.
- Освобождение ресурсов выполняется вручную, поэтому при исключении возможна утечка ресурсов.
- Чтение файлов и обработка записей тесно связаны, что затрудняет тестирование без файловой системы.
- Настройки и значения уровней логирования жёстко прописаны внутри класса.

## Устранение зависимости от типа приёмника (OCP)

**Проблема:** в исходном классе `LogProcessingModule` использовался оператор `switch` для выбора приёмника. При добавлении нового способа сохранения логов приходилось изменять существующий код.

**Решение:** был создан интерфейс `ILogSink`, определяющий общий метод `Write(LogRecord record)`. Для разных способов сохранения реализованы классы `InMemoryLogSink` и `FileLogSink`.

**Как работает:** класс `LogProcessor` принимает коллекцию приёмников через конструктор и передаёт каждой реализации объект `LogRecord`. Выбор конкретного приёмника выполняется за пределами `LogProcessor`.

**Результат:** устранена необходимость использовать `switch` для маршрутизации записей. Основной класс обработки не зависит от конкретного способа сохранения логов. Архитектура позволяет подключать новые реализации `ILogSink` без изменения логики `LogProcessor`.

## Выделение интерфейсов

**Решение:** в проекте создан интерфейс `ILogSink`, определяющий метод `Write(LogRecord record)`.

**Назначение:** интерфейс объединяет разные способы сохранения логов. Его реализуют классы `InMemoryLogSink` и `FileLogSink`.

**Почему остальные интерфейсы не добавлялись:** `LogFileReader`, `ApacheLogParser`, `SeverityFilter` и `PlainTextFormatter` имеют по одной реализации, которую в текущей архитектуре не требуется подменять.

**Результат:** интерфейс `ILogSink` позволяет использовать разные приёмники через общий контракт. При этом проект не перегружен лишними абстракциями.

### Результаты автоматического тестирования

1. **Parse_ValidLog_ReturnsRecord** — проверяет корректность разбора правильной строки Apache Combined Log и получения основных полей записи.

2. **Parse_ExtractsUserAgent** — проверяет правильное извлечение значения User-Agent из строки лога.

3. **Parse_InvalidLine_ReturnsNull** — проверяет, что при передаче некорректной строки парсер возвращает null.

4. **Parse_MissingResponseSize_ReturnsZero** — проверяет обработку отсутствующего размера ответа: вместо символа `-` записывается значение 0.

5. **InMemoryLogSink_Write_SavesRecord** — проверяет, что приёмник InMemoryLogSink сохраняет переданную запись в оперативной памяти.

6. **SeverityFilter_StatusBelowMinimum_ReturnsFalse** — проверяет, что фильтр отклоняет запись, HTTP-статус которой ниже установленного порога.

**Итог:** реализовано 6 автоматических тестов, проверяющих разбор логов, извлечение User-Agent, обработку некорректных данных, сохранение записей и фильтрацию.

## 6. Что стало проще и сложнее менять

**Стало проще:**

- Добавлять новые способы сохранения логов: достаточно создать новый класс, реализующий `ILogSink`.
- Менять способ чтения логов независимо от их обработки.
- Изменять правила фильтрации, не затрагивая парсер и приёмники.
- Изменять формат вывода отдельно от логики обработки записей.
- Тестировать парсер, фильтр и приёмники независимо друг от друга.

**Стало сложнее:**

- Для небольшого изменения теперь иногда приходится обращаться к нескольким классам вместо одного.
- При добавлении нового этапа обработки нужно правильно подключить его в `LogProcessor`.
- Для работы всей системы требуется настроить зависимости и передать нужные компоненты через конструкторы.

**Вывод:** после рефакторинга код стал более разделённым и удобным для расширения и тестирования. Небольшое увеличение количества классов компенсируется тем, что изменения в одной части системы меньше затрагивают остальные.
