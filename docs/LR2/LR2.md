# Лабораторная работа 5. IoC, DI-контейнер и Singleton

## Цель работы

Изучить различия между паттерном Singleton и управлением временем жизни объектов через DI-контейнер, применить внедрение зависимостей в приложении LogHub и проверить влияние общего состояния Singleton на тестируемость.

## Ход работы

### 1. Реализация конфигурационных сервисов

Создан интерфейс `IConfigService` с методами:

- `GetValue(string key)` — получение значения по ключу;
- `SetValue(string key, string value)` — сохранение значения.

Реализованы три варианта сервиса:

1. `ClassicConfigService` — классический Singleton с закрытым конструктором и общей статической точкой доступа `Instance`.
2. `LazyConfigService` — Singleton с отложенным созданием экземпляра через `Lazy<T>`.
3. `ConfigService` — обычный класс с публичным конструктором. Его экземплярами можно управлять через DI-контейнер.

### 2. Проверка общего состояния Singleton

В `LogHub.Tests/ConfigServiceTests.cs` добавлены проверки:

- классический Singleton возвращает один и тот же экземпляр;
- Singleton на основе `Lazy<T>` возвращает один и тот же экземпляр;
- два обычных `ConfigService` являются разными объектами и имеют независимое состояние;
- демонстрация зависимости тестов от общего состояния классического Singleton.

Для демонстрации два теста используют один ключ `order-test`. Первый записывает значение `saved`. Второй ожидает, что значение отсутствует. При отдельном запуске второго теста он проходит, а при запуске после первого получает сохранённое значение и падает. Это показывает, что результат теста зависит от состояния, оставленного другим тестом.

После демонстрации проблемный тест помечен атрибутом `[Fact(Skip = "...")]` с объяснением причины пропуска, чтобы намеренно проблемная проверка не ломала общий запуск тестового набора.

### 3. Композиционный корень и внедрение зависимостей в LogHub

В проект добавлен пакет `Microsoft.Extensions.DependencyInjection`.

В `Program.cs` создан композиционный корень приложения:

- зависимости `LogProcessor` зарегистрированы в `ServiceCollection`;
- `LogProcessor` получает `LogFileReader`, `ApacheLogParser`, `SeverityFilter`, `PlainTextFormatter` и набор `ILogSink` через конструктор;
- реализации хранилищ регистрируются в DI-контейнере;
- контейнер создаётся вызовом `BuildServiceProvider()`;
- `LogProcessor` извлекается из контейнера в точке входа приложения.

В рабочих классах нет обращений к `IServiceProvider`, `GetService` или `GetRequiredService`. Получение `LogProcessor` через `GetRequiredService` выполняется один раз в `Program.cs`. Создание сервисов приложения через `new` сосредоточено в композиционном корне.

### 4. Профили работы LogHub

Добавлен `ConsoleLogSink`, который форматирует запись и выводит её в консоль. Для файлового профиля используется существующий `FileLogSink`.

В `profile.txt` хранится выбранный профиль:

- `console` — вывод обработанных записей в консоль;
- `file` — запись обработанных записей в `logs.txt`.

`Program.cs` читает значение из `profile.txt` и регистрирует соответствующую реализацию `ILogSink`. В `LogHub.csproj` добавлена настройка `CopyToOutputDirectory` для копирования `profile.txt` в каталог сборки.

Переключение профиля выполняется изменением содержимого `profile.txt` и перезапуском приложения. Перекомпиляция для смены профиля не требуется.

### 5. Проверка работы

Для проверки обработки использован файл `LogHub/access.log` с двумя корректными строками Apache-лога. После исправления формата строк под регулярное выражение `ApacheLogParser` приложение обработало обе записи.

Результат запуска профиля `console`:

- записано: 2;
- пропущено: 0;
- сохранено в памяти: 2.

Затем значение в `profile.txt` изменено с `console` на `file`. Приложение повторно запущено командой `dotnet run --no-build --project LogHub -- LogHub/access.log`, то есть без пересборки. Файловый профиль отработал и записал записи в `logs.txt`.

## Ответ на контрольный вопрос: чем Singleton отличается от AddSingleton в DI-контейнере и почему второй вариант лучше тестируется?

Классический Singleton сам управляет созданием и предоставлением единственного экземпляра. Обычно для этого используются закрытый конструктор и статическое свойство или метод доступа. Код, которому нужен такой объект, обращается к глобальной точке доступа. Из-за этого потребитель жёстко связан с конкретной реализацией и общим состоянием. В тестах состояние может сохраняться между проверками, а подменить Singleton альтернативной реализацией или изолировать его состояние сложнее.

`AddSingleton` — это регистрация сервиса в DI-контейнере с временем жизни Singleton. Контейнер создаёт или получает экземпляр и повторно использует его в пределах времени жизни соответствующего `IServiceProvider`. При этом сам класс не обязан быть статическим Singleton: он может иметь обычный публичный конструктор и реализовывать интерфейс.

Такой вариант лучше тестируется, потому что зависимость передаётся потребителю через конструктор. В тесте можно создать отдельный контейнер, зарегистрировать другую реализацию `IConfigService` или новый экземпляр `ConfigService` и тем самым изолировать состояние. Потребитель зависит от интерфейса, а не от глобальной статической точки доступа.

Таким образом, Singleton в обоих случаях означает повторное использование экземпляра, но классический Singleton скрывает управление экземпляром внутри самого класса, а `AddSingleton` поручает управление временем жизни DI-контейнеру. Именно явное внедрение зависимости и возможность заменить реализацию делают вариант с DI удобнее для тестирования.
